# BlockVault architecture

## Modules and dependencies

- **`core`** is plain Java: encrypted vault/file handling, account and backup models, validation, prompt/result matching, password generation, and the `LoginSession` state machine. It has no Minecraft or loader dependency.
- **`shared-client`** adapts core to Minecraft: client configuration and screens, `Hooks`, `VaultRuntime`, UI/session callbacks, and mixins. It may depend on core and Minecraft APIs, but not on Fabric or NeoForge APIs.
- **`fabric`** and **`neoforge`** register their loader events and initialize the shared client. They may depend on shared-client and their respective loader API; shared-client and core must not depend on either loader. Both loader builds compile the shared/core source roots into their mod.
- **`core/build.gradle`** is the isolated Java/JUnit build. Loader Gradle files include core and shared-client source/resource directories in the loader mod source set.

```text
Server messages: Fabric / NeoForge event
    -> Hooks -> LoginSession -> VaultAccess (VaultRuntime)
    -> VaultRuntime background IO -> VaultStore -> vault files
    <- callbacks marshalled to Minecraft game thread -> McSessionEnv / screens

Typed command: command/history mixins -> Hooks -> LoginSession
    -> VaultAccess lookup/save -> explicit card confirmation when needed
    -> Hooks.sendOwnCommand -> Minecraft connection (suppress manual capture)
```

## Message and command flow

The loader adapters pass system messages (including action-bar messages) to `Hooks`; player chat is excluded by the loader/mixin path. `Hooks` buffers early join messages while patterns and settings load, then forwards eligible messages to the connection's `LoginSession`. The session owns prompt/result decisions and asks its `SessionEnv` to display cards or send commands. Its `VaultAccess` is `VaultRuntime`.

Vault operations enter `VaultRuntime`, which schedules file and cryptographic work on `BackgroundExecutor`'s single-thread IO executor. `VaultStore` reads/writes encrypted files and backups. Results that update a screen or session are posted back to the game thread before invoking the UI/session callback.

The outgoing-command mixin calls `Hooks.onOutgoingCommand`. `Hooks` identifies sensitive command names and whether a short alias was explicitly prompted, then delegates command parsing and command-result state to `LoginSession`. A command generated by BlockVault is sent through `Hooks.sendOwnCommand`, which marks the send as internal so it is not captured as a manual command. The command-history mixin consults `Hooks`/`SensitiveCommands` to scrub secrets from history.

## Thread ownership and mutable state

The ownership contract is: **Minecraft screens, widgets, loader callbacks, `Hooks` session state, `LoginSession`, and `McSessionEnv` are game-thread state. Vault file access, JSON serialization, KDF, encryption, backup work, and password verification run on the single `blockvault-io` executor. Timer callbacks are scheduled separately and dispatched back to the game thread.** `VaultStore` is thread-confined: in the client it is owned by the IO executor; core tests may call it from their test thread.

Shared mutable state currently has these owners:

- **`Hooks`:** connection/session fields (`session`, `environment`, host/user, error count, queued join messages/prompt, settings-loaded and pattern-loading flags, connection revision) are game-thread owned. The immutable `PatternPack` and sensitive-alias set are published through volatile references and read by the command hook. `SELF_SENT` and `HISTORY_SCRUBBED` are thread-local markers for the command/history hook invocation. Hook-warning flags and `commandHookSeen` are mutated by hook calls; warning decisions are made on the game/command thread.
- **`LoginSession`:** all fields, pending credentials, state, debounce/revision counters, and alias sets belong to the game thread. `Scheduler` posts timer callbacks there; `VaultAccess` callbacks must also arrive there.
- **`McSessionEnv`:** active/waiting card, queued prompts, showing state, and wait handle belong to the game thread. Scheduled poll callbacks return to it.
- **`VaultRuntime`:** the `VaultStore` reference and all `VaultStore` calls belong to the IO executor. `WAITING` is a concurrent deque because enqueue/drain spans IO and UI paths. Access/unlock/trust booleans are volatile coordination flags read/written from IO and game-thread paths. `vaultReturnScreen` is captured by UI navigation and passed through the unlock flow; preserve that handoff when refactoring it. Toasts, screen changes, and screen callbacks are game-thread work.
- **`BlockVaultConfig`:** `current` is an immutable settings record published via a volatile reference. `loaded` and disk reads/writes are managed by IO tasks; UI/session consumers receive completion callbacks on the game thread. The background executor and timer executor are lazily initialized under synchronization.
- **`VaultStore`:** instance fields (`header`, wrapped/unwrapped keys, active vault, pending import, and disk digest) are only accessed by the owning storage thread. Password/key byte arrays are copied or wiped at ownership boundaries.
- **Screens and screen-local mutable fields:** game thread only. They hand work to `VaultRuntime` and receive results via game-thread callbacks.

Do not move KDF/file work onto the game thread or invoke screen/session callbacks directly from the IO executor.

## Settings and persisted data

| Data | Location | Notes |
|---|---|---|
| Client preferences (autofill, passwordless login, delay, card position, streamer/hide-address mode, generator, history scrubbing, trusted-device choice, card animations) | `<BlockVault data directory>/config.json` | Non-secret client settings. |
| Trusted-device key | `<BlockVault data directory>/vault.bv.trust` | Local key material managed by `VaultStore`; distinct from the encrypted vault and settings. |
| Vault, accounts, trash, account preferences | `<BlockVault data directory>/vault.bv` | Encrypted vault payload. Account autofill/template preferences live in account metadata. |
| Prompt patterns | `<BlockVault data directory>/patterns.json` plus bundled `assets/blockvault/patterns/default.json` | User file extends the bundled rules. |
| Backups and exports | Under the BlockVault data directory by default; exports may use a selected folder | Backup copies remain encrypted. |

## Legacy and migration code

- `ServerEntry.autofill` and `ServerEntry.templateId` remain in the serialized/server model for legacy compatibility; `VaultJson` migrates their values into per-account metadata when those preferences are absent.
- Account metadata preserves unknown fields for forward compatibility; `AccountPreferences` stores per-account autofill and command-template preferences there.
- `VaultFile.Header.keyModeId` is part of the encrypted-file header and its validation/compatibility path. Do not remove or reinterpret it as cleanup.
- JSON parsing retains malformed account records as unusable entries so their data is not silently discarded.

## Where to change X

| Change | Start here |
|---|---|
| Add or edit a prompt/result pattern | `shared-client/src/main/resources/assets/blockvault/patterns/default.json` for bundled rules; `PromptMatcher` / `ResultMatcher` for matching behavior. |
| Add a credential/settings screen | `shared-client` screen classes; use the existing navigation/runtime entry points and keep all screen changes on the game thread. |
| Change encrypted vault format or account migration | `core/.../vault/VaultFile`, `VaultJson`, `VaultStore`, with compatibility tests in `core/src/test`. |
| Add a client setting | `BlockVaultConfig.Settings` read/write/defaults, then the native settings and optional YACL screen controls and translations. |
| Change loader event registration | The corresponding `fabric/.../FabricClientHooks` or `neoforge/.../NeoForgeClientHooks`; keep common behavior in `Hooks`/`LoginSession`. |
| Change command detection/session behavior | `Hooks` for Minecraft event adaptation; `core/.../session/LoginSession` for pure state decisions. |
